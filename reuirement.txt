PROJECT NAME

IntelliDoc

CORE IDEA

IntelliDoc is a client-side scanned-document OCR, reconstruction, and editing application.

The main idea is simple:

A user uploads a scanned document image or PDF.

The application reads the document using OCR.

It detects the text, position, layout, typography, colors, spacing, and other visual characteristics.

The user can then edit the recognized text directly in the document.

When text is changed, IntelliDoc should remove or reconstruct the original text area and render the new text so that it visually matches the original document as closely as technically possible.

The final result should look like the same original document with the text legitimately changed, rather than looking like new computer-generated text placed on top of a scanned image.

Example:

Original:

Date: 13-09-2024

User changes it to:

Date: 19-07-2026

The resulting document should preserve the original document’s visual characteristics, including typography, size, weight, color, spacing, alignment, position, background, texture, scan quality, and other relevant characteristics.

This is NOT simply an OCR-to-text application.

It is a visual document reconstruction and editing system.

# **MAIN PRODUCT GOAL**

The highest-priority goal is:

CHANGE TEXT WHILE PRESERVING THE ORIGINAL VISUAL APPEARANCE.

The system should attempt to reproduce:

- Font family or closest visual font
- Font size
- Font weight
- Italic/normal style
- Text color
- Opacity
- Character spacing
- Word spacing
- Line spacing
- Baseline
- Text width
- Text height
- Horizontal scaling
- Vertical scaling
- Rotation
- Alignment
- Position
- Stroke/thickness appearance
- Anti-aliasing appearance
- Local scan texture
- Background texture
- Paper color
- Shadows
- Noise
- Compression artifacts
- Other characteristics visible in the original scan

The system should not assume that the original font metadata exists.

A scanned image usually contains pixels rather than actual font information.

Therefore, IntelliDoc must estimate the visual characteristics from the pixels.

The goal is visual matching, not merely identifying a font name.

# **IMPORTANT PRINCIPLE**

Never solve a visual reconstruction problem with a simple text overlay if a better reconstruction method is possible.

Do not simply:

1. Detect text.
2. Put a white rectangle over it.
3. Draw Arial text.
4. Export.

Instead:

1. Detect the original text region.
2. Analyze the original pixels.
3. Understand the surrounding background.
4. Remove or mask the original text.
5. Reconstruct the background.
6. Analyze typography.
7. Generate candidate replacement renderings.
8. Compare candidates with the original visual characteristics.
9. Optimize the rendering.
10. Composite the replacement into the document.
11. Preserve the natural appearance of the scan.

# **OCR ENGINE**

OCR is responsible for recognizing document content.

OCR should preserve more than just text.

The OCR system should attempt to provide:

- Text
- Words
- Lines
- Paragraphs
- Bounding boxes
- Confidence
- Reading order
- Page number
- Orientation
- Rotation where possible

OCR processing should occur in a Web Worker.

The UI must remain responsive while OCR is running.

The application should show meaningful processing progress.

Low-confidence OCR should be visually identifiable to the user.

The user must be able to manually correct OCR results.

OCR and visual reconstruction are separate systems.

Do not assume that accurate OCR automatically produces accurate document reconstruction.

# **VISUAL FIDELITY ENGINE**

Visual fidelity is a P0 requirement.

The replacement text must attempt to match the original text visually.

The system should analyze the original text region before modifying it.

Analyze:

- Glyph appearance
- Stroke thickness
- Character width
- Character height
- Text density
- Darkness
- Color
- Spacing
- Baseline
- Alignment
- Rotation
- Local texture
- Background
- Noise
- Scan artifacts

The system should generate candidate renderings and compare them against the original region.

Candidate parameters may include:

- Font
- Font size
- Font weight
- Italic
- Color
- Opacity
- Letter spacing
- Word spacing
- Horizontal scaling
- Vertical scaling
- Position
- Baseline
- Rotation
- Rendering method

The system should iteratively adjust these parameters to improve visual similarity.

Do not rely on one fixed font.

Do not default to Arial unless the analysis determines that it is visually appropriate.

# **FONT IDENTIFICATION**

Font identification is an important part of the system.

However, a scan does not normally contain the original font metadata.

Therefore, the application should distinguish between:

1. Actual known font metadata
2. Estimated font characteristics
3. Visually similar candidate fonts

When possible:

- Identify likely font families
- Compare glyph shapes
- Compare stroke characteristics
- Compare proportions
- Compare character widths
- Compare serif/sans-serif characteristics
- Compare x-height
- Compare ascenders/descenders
- Compare weight
- Compare spacing

If the exact font cannot be determined, optimize for visual similarity rather than claiming certainty.

# **TEXT REPLACEMENT**

When the user edits text:

1. Store the new text in the document model.
2. Identify the original text region.
3. Preserve its visual parameters.
4. Determine the new text dimensions.
5. Reconstruct the original background.
6. Render the replacement text.
7. Adjust typography to fit the original region.
8. Compare the result with the original style.
9. Optimize the rendering.
10. Composite the result.

If the new text is longer or shorter, intelligently adapt it.

Possible adjustments:

- Font size
- Horizontal scaling
- Letter spacing
- Word spacing
- Text box width
- Alignment

Do not distort text unnecessarily.

The system should prefer natural typography before aggressive scaling.

# **BACKGROUND RECONSTRUCTION**

Do not simply cover removed text with a solid white rectangle.

The background may contain:

- Paper texture
- Grayness
- Shadows
- Gradients
- Lines
- Tables
- Printed patterns
- Stamps
- Noise
- Compression artifacts
- Scanning artifacts

The system should analyze nearby pixels and reconstruct the text region appropriately.

Possible techniques include:

- Local background estimation
- Masking
- Inpainting
- Texture synthesis
- Neighbor-based reconstruction
- Edge-aware reconstruction
- Noise preservation

The reconstructed region should blend naturally with the surrounding document.

# **ERROR HANDLING**

Never silently fail.

If OCR fails:

Explain the problem and allow retry/manual editing.

If a font cannot be identified:

Use the closest visual candidate and communicate that it is an estimate.

If reconstruction is uncertain:

Provide a fallback rather than corrupting the original.

If a document is too large:

Warn the user and offer progressive processing where possible.

If PDF parsing fails:

Explain the issue without exposing technical errors unnecessarily.

Always preserve the original.

CLIENT-SIDE VISUAL DOCUMENT RECONSTRUCTION SYSTEM
